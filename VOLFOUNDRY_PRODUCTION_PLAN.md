# VolFoundry Production & Distribution Upgrade Plan

> **Purpose:** This file is an execution specification for an AI coding agent working on the current `gavinwunz/volsurface` repository. The goal is to transform it into **VolFoundry**, a trustworthy, installable, well-documented, production-quality open-source Python library for volatility-surface construction, options pricing, calibration, diagnostics, and research.
>
> **Brand:** VolFoundry  
> **PyPI distribution:** `volfoundry`  
> **Python import package:** `volfoundry`  
> **CLI command:** `volfoundry`  
> **Target first public release:** `v0.1.0`

# 0. AI AGENT OPERATING INSTRUCTIONS

You are the lead maintainer responsible for taking this repository from a strong research prototype to a credible public open-source package.

Work autonomously. Do not ask for approval for routine engineering decisions. Inspect the current repository before changing anything and preserve working quantitative functionality unless there is a demonstrated correctness issue.

## Non-negotiable rules

1. **Correctness before features.** Quantitative correctness, numerical stability, reproducibility, and honest claims matter more than adding functionality.
2. **Never fabricate benchmarks, test counts, accuracy figures, supported platforms, or performance claims.** Every number in the README must be generated by a command that can be rerun.
3. **Do not claim “arbitrage-free” unless the returned production surface satisfies the implemented analytical constraints and validation contract.** Numerical diagnostics alone must not be marketed as a mathematical guarantee over the entire real line.
4. **No silent failure.** Calibration failures, invalid quotes, arbitrage violations, optimizer non-convergence, malformed API responses, and fallback behavior must be explicit and inspectable.
5. **No hidden network activity.** Importing `volfoundry` must never call external APIs. Live market-data access happens only through an explicit user action.
6. **No telemetry.** Do not add analytics, tracking, or outbound telemetry.
7. **Keep the pure-Python path fully functional.** The C++ acceleration path must remain optional. A user should not need a compiler to install and use the core package.
8. **Tests must validate behavior, not merely implementation details.** Retain the existing property-based and benchmark-oriented philosophy.
9. **Each milestone must leave the repository in a passing state.** Run the full relevant test suite before committing.
10. **Use small, reviewable commits.** Suggested milestone commit names are provided below.
11. **Do not delete the mathematical derivations.** Improve and reorganize them where necessary.
12. **Do not break a valid numerical routine simply to make the architecture prettier.** Refactor only with regression coverage.
13. **Prefer standard library + existing dependencies.** Introduce new runtime dependencies only when they solve a clear user-facing problem.
14. **All dates and timestamps must be timezone-aware UTC internally.**
15. **All public APIs require docstrings, types, validation, and documented error behavior.**

Run and record:

# 1. TARGET PRODUCT DEFINITION

VolFoundry should become:

> **Open-source volatility infrastructure for derivatives: market data → implied volatility → calibrated surfaces → arbitrage validation → pricing and risk.**

The first production-quality release should focus on doing the existing scope extremely well rather than expanding into many new models.

## Primary user personas

### Quant researcher
Needs to obtain live or supplied option quotes, calibrate a volatility surface, inspect diagnostics, query implied volatility, and reproduce results.

### Quant developer
Needs stable functions/classes that can be embedded in research or pricing infrastructure without relying on notebooks or plotting code.

### Student / educator
Needs readable derivations, deterministic examples, transparent formulas, and clean separation between theory and implementation.

### Crypto derivatives researcher
Needs a reliable Deribit adapter, snapshot persistence, quote cleaning, BTC/ETH surface construction, and historical reproducibility.

## Explicitly out of scope for v0.1.0

Do not pretend VolFoundry is a full institutional trading/risk platform. v0.1.0 does **not** need:

- trade execution;
- portfolio accounting;
- exchange authentication/private endpoints;
- real-time websocket streaming;
- distributed computing;
- production market-making;
- P&L systems;
- order management;
- regulatory reporting;
- guaranteed suitability for live capital deployment.

# 2. CURRENT REPOSITORY ISSUES TO FIX

The repository currently has several characteristics of a research prototype that must be addressed before broad distribution:

- project/package branding is `volsurface`, not VolFoundry;

- contributor/security/release documentation is incomplete;
- reproducible wheel/sdist installation is not yet the central tested workflow.

The upgrade must address these systematically.

**Suggested commit:** `feat: add stable high-level VolFoundry API`

The current implementation contains useful lower-level modules, but a user should not need to understand repository internals to build a surface.

## Public API principles

- Keep low-level quantitative modules importable for advanced users.
- Add a deliberate high-level API.
- Avoid exporting dozens of implementation details from the package root.
- Use dataclasses or frozen data objects for result structures where appropriate.
- Separate data acquisition from calibration.
- Make offline usage a first-class path.

## Target high-level concepts

Implement or adapt clean equivalents of:

```python
from volfoundry import (
    DeribitClient,
    SurfaceBuilder,
    VolatilitySurface,

```

The exact internals may differ, but the user experience should be similar to:

```python
from volfoundry import DeribitClient, SurfaceBuilder

snapshot = DeribitClient().fetch("BTC")

surface = result.surface
report = result.validation

print(surface.iv(strike=70_000, maturity=30 / 365.25))
print(report.is_valid)
```

Also support offline data:

```python
surface_result = SurfaceBuilder().fit_dataframe(df)
```

or an explicitly typed `OptionChain` object.

Do not force users to call Deribit merely to access calibration functionality.

## Required result objects

Create explicit structured outputs rather than loose dictionaries where practical.

### `SurfaceFitResult`

Should expose at least:

- fitted surface;
- calibration status;
- optimizer diagnostics;
- quote-cleaning statistics;
- forward estimates;
- per-expiry diagnostics;
- global diagnostics;
- validation report;
- source snapshot metadata;
- warnings.

### `ValidationReport`

Should expose at least:

- `is_valid`;
- butterfly check result;
- calendar check result;
- density cross-check result;
- analytical condition status where applicable;
- numerical tolerances used;
- evaluation domain;
- rejected slices / reasons;
- warnings.

### `MarketSnapshot` / `OptionChain`

Should expose:

- currency/underlying;
- retrieval timestamp UTC;
- source;
- raw quote count;
- quote records/dataframe conversion;
- schema version if persisted.

## Root exports

Keep `src/volfoundry/__init__.py` intentionally small. Export stable high-level objects only.

Define `__all__`.

## Acceptance criteria

A new user can perform the main workflow in fewer than ~15 lines of Python without importing an internal submodule.

# 8. MILESTONE P5 — MAKE MARKET DATA RELIABLE

**Suggested commit:** `refactor: harden Deribit market-data ingestion`

The market-data layer is a production boundary. Treat external responses as untrusted input.

## HTTP requirements

For all Deribit calls:

- explicit connect/read timeout;
- reusable session/client;
- descriptive `User-Agent` including VolFoundry version;
- retry only safe/idempotent public requests;
- bounded retries;
- exponential backoff with jitter;
- retry 429 and appropriate transient 5xx failures;
- do not endlessly retry invalid JSON or schema errors;
- surface the final error through `MarketDataError`;
- validate JSON-RPC error fields;
- validate required response fields before conversion;
- never suppress an API error and return an empty chain as if successful.

## Quote schema

Create a typed boundary representation for raw quote data.

Validate:

- finite numeric prices;
- positive strike;
- valid option type;
- timezone-aware expiry;
- timezone-aware retrieval timestamp;
- non-negative bid/ask where appropriate;
- ask >= bid unless explicitly retained for diagnostics;
- finite underlying/index prices;
- source instrument name parsing.

## Quote cleaning

Do not merely return a smaller dataframe. Return cleaning diagnostics.

Example:

```text
raw:                 794
removed_zero_bid:     41
removed_crossed:       2
removed_near_expiry:  36
removed_invalid:       4
retained:             711
```

Every removed quote should have a machine-readable reason available if detailed diagnostics are requested.

## Snapshot persistence

Persist sufficient metadata to reproduce a result later:

- source;
- retrieval timestamp;
- package version;
- schema version;
- currency;
- raw quotes;
- underlying/index fields required for reconstruction.

Use atomic writes:

1. write temp file;
2. fsync/close where relevant;
3. move/replace to final path.

Never overwrite a historical snapshot by default.

## Offline tests

Most data-layer tests must use fixture responses and must not depend on live Deribit availability.

Live integration tests should be separately marked:

```python
@pytest.mark.live
```

and excluded from the default deterministic unit suite.

# 9. MILESTONE P6 — FIX THE “ARBITRAGE-FREE” CONTRACT

**Suggested commit:** `fix: enforce validated no-arbitrage surface construction contract`

This is the most important quantitative production change.

## Problem to solve

Do not equate:

```text
fit surface → check it → print PASS/FAIL
```

with:

```text
constructor returns a surface satisfying its advertised no-arbitrage contract
```

The production API must make this distinction explicit.

## Required design

Provide two explicit concepts:

### Unconstrained / research fit

Useful for diagnostics and comparison.

```python
result = builder.fit(..., validation="report")
```

This may return a fitted model with `report.is_valid == False`, but it must clearly identify that the surface is invalid.

### Strict production fit

```python
result = builder.fit(..., validation="strict")
```

This must **not** silently return an invalid surface.

If the required conditions are not met after allowed calibration/recalibration strategies:

```python
raise ArbitrageViolationError(...)
```

or return a failed result only if the API explicitly uses a non-throwing result model.

## SSVI analytical constraints

Review the Gatheral–Jacquier SSVI conditions in the derivation and implementation.

Where analytical sufficient conditions are available for the chosen `phi(theta)` family, enforce them during parameter search or reject candidate parameters before a result is considered valid.

Do not merely compute a Lee-style bound after optimization and print whether it passed.

At minimum:

- enforce `rho` domain;
- enforce positive `theta`;
- enforce valid `eta` / lambda domain for the selected formulation;
- enforce monotone ATM total variance with maturity or explicitly repair/recalibrate it using a documented method;
- enforce the analytical sufficient conditions required by the chosen SSVI parameterization;
- verify numerical calendar/butterfly behavior over a documented stress domain as an additional diagnostic.

If a monotonic repair such as isotonic regression is introduced for `theta(T)`, preserve both:

- raw market-estimated theta;
- adjusted theta used by the valid surface;

and report the adjustment magnitude. Never silently modify observed inputs.

## Raw SVI behavior

Raw SVI slice fits may be useful even when a slice violates a global condition. Therefore:

- expose per-slice fit status;
- expose `g(k)` minimum and evaluated domain;
- distinguish “fit converged” from “fit valid”;
- do not automatically label every optimizer success as usable.

## Numerical validation domain

Every numerical no-arbitrage report must state the domain, e.g.:

```text
k ∈ [-2.0, 2.0], 1001 points
```

Do not claim numerical grid validation proves all-real-line behavior.

## Breeden–Litzenberger

Treat finite-difference density as a **cross-check**, not the sole proof of no butterfly arbitrage.

Document sensitivity to:

- strike spacing;
- finite difference resolution;
- interpolation;
- wing behavior;
- numerical tolerance.

## README wording after this milestone

Use precise wording such as:

> “VolFoundry can construct SSVI surfaces under enforced model constraints and provides explicit static-arbitrage validation diagnostics. Numerical checks are reported with their evaluation domain and tolerance.”

Avoid unconditional marketing statements that exceed what is mathematically implemented.

## Acceptance tests

Add tests proving:

1. deliberately invalid SVI parameters are detected;
2. deliberately calendar-crossing slices fail strict validation;
3. strict mode refuses invalid returned surfaces;
4. report mode preserves invalid fits for research while clearly marking them invalid;
5. analytically valid SSVI examples pass;
6. optimizer failure is distinguishable from arbitrage failure;
7. tolerance changes are reflected in report metadata.
